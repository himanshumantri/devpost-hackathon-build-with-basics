Two programs side by side: a React frontend you see, and a small Python (FastAPI) backend that holds the data and applies the matching rules.

The big picture: two places they talk

Only two requests happen in a normal run. Everything else, including chat, stays in the browser.

Follow one person through the system

How the matching works (backend, matching.py)

  • Filter: same airport and boarding time within 60 minutes (same day).
  • Interest rule: a shared interest; or either has "Just open to talk"; or both have one of Startups / Technology / Markets.
  • Venue rule: either has "Any place is good"; or both have Bar/Restaurant; or both have Cafe/Lounge.
  • Keep anyone passing the interest rule or the venue rule.
  • Sort: closest boarding time, then interest match first, then venue match first. Keep five.
The two API calls in detail

GET /api/airports → list of airports.

[ { "code": "LHR", "name": "London Heathrow Airport", "city": "London", "country": "United Kingdom" }, … ]

POST /api/matches

request: { "airport_code": "LHR", "boarding_time": "18:00",
           "interests": ["Startups"], "venues": ["Cafe"] }
reply:   { "matches": [ { "id", "name", "profession", "interests",
           "favorite_place", "boarding_time",
           "matched_on_interest", "matched_on_venue" } ] }

A badly formed request gets a 422 reply automatically. FastAPI also serves a test page at /docs.

Stack, how to run, and look and feel
  • Frontend: React 18 + Vite, plain JavaScript and CSS (react.dev, vite.dev).
  • Backend: Python 3.11, FastAPI, Uvicorn, Pydantic, pytest (fastapi.tiangolo.com).
  • Run: terminal 1: cd backend, create a venv, pip install -r requirements.txt, uvicorn app.main:app --reload --port 8000. Terminal 2: cd frontend, npm install, npm run dev. Open http://localhost:5173.
  • Demo: London Heathrow, boarding between about 5:00 and 7:00 PM, interests like Startups + Cafe. For "no matches," pick another airport or a distant time.
  • Look: white background, dark text, rounded friendly sans-serif, green buttons with white text, initials avatars for sample people, departures picture only on Welcome.

If something goes wrong
  • Backend not running → "Can't reach the server. Is the backend running?" with Retry; Start stays disabled.
  • No matches → "No matches found. Start over and try expanding your interests & choices" plus Start Over.
  • Session storage unavailable → chat works for this visit but isn't remembered.
  • Camera capture on desktop → standard browser behavior (file picker on desktop, camera on phone); no special handling.
What was simplified and why
  • Pre-made sample people instead of real users (needs a shared database and live updates).
  • Fixed boarding times so the demo is predictable.
  • JSON files instead of a database; no login; session storage instead of a chat server.
  • Initials avatars for sample people; screens chosen by a state value instead of a router.
